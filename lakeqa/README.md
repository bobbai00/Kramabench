# LakeQA Phase A adoption

Runs the Texera dataflow agent on a stratified 24-task subset of
[LakeQA](https://arxiv.org/abs/2606.10460) mini (ICML 2026), **oracle-style**:
each task is handed its own source files locally, mirroring KramaBench oracle
mode. This isolates the *reasoning/pipeline* half of LakeQA — the search half
(million-scale lake, their headline dimension) is deliberately out of scope
until Phase B adds search/download tools to the agent.

## Why these 24 tasks

From the 135 mini tasks (see `subset_24.json`, generated by `prepare.py`):

- **table-dominant only** — wikipedia files ≤ 1/3 of the task's sources
  (119/135 qualify); the dataflow operators are table-centric.
- **no .pdf/.docx** sources.
- **k ∈ {3,4,5}** reasoning hops (120/135 of mini), **8 per k**, round-robin
  over `d` (file breadth, 10→21 files/task) so difficulty is spread.
- **≤ 500 MB of sources per task** (same-stratum backfill): the mini set has
  a few multi-GB data.gov dumps that would dominate download + execution
  time; Phase A is a reasoning smoke, not an I/O benchmark. Kept range:
  0.4–470 MB/task, 1.48 GB total across 243 distinct files.

## Layout & compatibility

- Data: `data/lakeqa/input/<s3-key>` (gitignored; refetch with
  `prepare.py --download`). The `dataflow-agent/data -> Kramabench/data`
  symlink makes `data/lakeqa/...` paths readable by the agent's operators.
- Scratch: `system_scratch/LakeQA_<SUT>/<question_id>/` with the full
  standard artifact set (prompt/config/react_steps/workflow/stats/answer/
  response/ground_truth/evaluation) — **all kb.py tooling works unchanged**
  (`cost`, `tokens`, `traces`, `venn`, `case-metrics` take
  `LakeQA_<SUT>` as the SUT name).
- Scoring: LakeQA's own `evaluation.llm_judge` (gpt-5-mini, imported from the
  clone at `~/Desktop/bobflow/lakeqa`, override with `LAKEQA_REPO`).
  `evaluation.json` = `{"success": 0|1, llm_judge_*...}`; ground truth is
  written as `answer_type: string_exact`, so `kb.py` `answer_scores` reads
  LakeQA results through the same path as KramaBench.

## Running

Texera stack + agent-service must be up (see dataflow-agent CLAUDE.md), plus
`OPENAI_API_KEY` in `./.env` (judge). Uses the **combined venv** — the
dataflow-agent uv project with the `lakeqa` extra (`uv sync --all-extras`):

```bash
PY=~/Desktop/bobflow/dataflow-agent/.venv/bin/python
$PY lakeqa/prepare.py --download          # once: select subset + fetch data
$PY lakeqa/run_lakeqa.py --parallel 3     # full subset
$PY lakeqa/run_lakeqa.py --ids "EQA000229" --parallel 1   # one task
$PY lakeqa/run_lakeqa.py --skip-done ...  # resume (skips tasks with evaluation.json)
```

## Caveats

- One run ≠ calibrated: no LakeQA twin-noise floor exists yet — per
  `judgment_runs/COMPARISON_PIPELINE.md`, run an identical-config rerun pair
  before comparing arms.
- `answer.json` is parsed from the agent's `Final Answer:` line; the judge
  enforces LakeQA's format constraints (exact numerics, ordering, no-acronym
  rules), so KramaBench-style near-misses grade as failures.
- Deleted-probe accounting, chronic-flipper gating, and the cost cohorts all
  carry over via the standard artifacts once twin pairs exist.
